## FE 동의 방향과 미합의 부분

동의 가능한 설계 방향: 최소 수집 자기 확인, 누락/false 거절, 정책 버전과 서버 확인 시각, 실제 동의 항목 분리, 기존 사용자 자동 동의 금지, additive 배포 후 강제 적용.

아직 확정하지 않는 사항: 필드명·경로·HTTP 상태/오류 코드·최초 정책 version·임시 계정 수명·기존 사용자 재확인 기한/제한 범위·변경/철회 보존 기간·법적 처리 근거와 실제 동의 항목. 아래 JSON은 계약 협의용이며 현재 서버가 제공하는 응답이 아니다.

## 화면·라우팅 제안

현재는 각 로그인 handler와 앱 초기 인증에서 `requires_profile_setup`으로 프로필/캘린더를 분기한다. 새 정책 확인을 프로필 완료 boolean에 합치지 않는다.

```text
앱 시작·로그인 성공·프로필 재개
 → 서버의 정책 상태 조회
 → 클라이언트 미지원 → 업데이트 안내
 → 확인 필요 → 정책 확인 화면
 → 프로필 미완료 → 기존 프로필 화면
 → 둘 다 완료 → 메인 캘린더
```

- 공통 진입 판단을 application 계층에 두고 4개 로그인 handler·앱 재실행·딥링크에서 같은 기준 사용. UI 내 조건만으로 보호하지 않으며 BE도 강제 검증.
- 인증 토큰 존재와 서비스 이용 가능은 별개. 미확인 계정은 정책 조회/확인·로그아웃·정책/지원 열람·탈퇴 등 합의한 최소 기능만 접근한다.
- 제한 상태에서도 개인정보처리방침·지원 연락처를 열 수 있어야 함. 네트워크 오류를 동의 완료로 처리하지 않음.
- 신규 사용자는 OAuth 시작 전에 14세 이상 자기 확인을 안내하는 방향. 제공자 계정 소유 확인 후 서버 기록과 결합하는 세부 계약은 BE와 확정. 앱의 자기 확인은 실제 나이 검증이 아님.
- 기존 사용자는 서버 미확인 상태를 그대로 표시. 거절·뒤로가기·구버전 업데이트·기한 유예 범위는 운영자 결정 전 임의 적용 금지.
- 미정의 이용약관 URL이나 최종화 전 개인정보처리방침을 확정 문서로 제시하지 않음. 단순 ‘로그인하면 모두 동의’ 문구는 항목별 처리 근거에 맞춰 교체.

## UI state와 domain state

- UI 전용: 화면 체크 선택·확장 상태·전송 중·화면 오류. 사용자가 체크한 값만으로 영속 동의 완료를 판단하지 않음.
- domain: 서버 상태, 필수 정책 version, 항목별 확인/동의 결과·현재 기능 제한·프로필 미완료 상태.
- provider는 계정 변경/로그아웃/탈퇴 시 무효화. 조회·제출 중 중복 요청 제한, dispose 뒤 화면 업데이트 금지.
- 미확인/조회 실패/제출 중/완료/버전 변경/업데이트 필요를 구분. 실패에 대해 자동 true·로컬 캐시만으로 통과하는 fallback 없음.

## 조회·제출 DTO 협의 초안

경로는 기존 `/auth/profile` 확장 또는 별도 인증된 상태 endpoint 중 BE가 영향 분석 후 제안한다. 조회와 제출은 인증 필요이며 제한 계정에서도 필요한 접근 허용.

조회 응답 후보:

```json
{
  "policy_status": "REQUIRED",
  "policy_version": "VERSION_TO_BE_AGREED",
  "age_confirmation_required": true,
  "required_actions": ["AGE_CONFIRMATION", "PRIVACY_NOTICE"],
  "consent_items": [
    {"code": "ITEM_TO_BE_CONFIRMED", "required": false}
  ],
  "accepted_at": null
}
```

제출 후보:

```json
{
  "policy_version": "VERSION_TO_BE_AGREED",
  "is_age_14_or_over": true,
  "privacy_notice_acknowledged": true,
  "consents": [
    {"code": "ITEM_TO_BE_CONFIRMED", "agreed": false}
  ]
}
```

- 모든 필드명·enum은 후보. 항목 코드는 실제 법적 근거·목적 확정 뒤 정의하며 예시 코드를 API에 보내지 않음.
- 개인정보 안내 확인은 실제 동의와 다른 개념. 서비스 계약에 따른 처리·선택 동의·공유·국외 이전을 하나의 true로 묶지 않음.
- 서버가 결정한 version만 제출. 클라이언트 확인 시각은 보내지 않고 서버가 기록. 위변조/문자열 `"true"`/null/배열 중복/미지원 항목은 서버 검증.
- 성공 응답은 서버의 최종 상태·version·확인 시각을 반환해야 FE가 동기화 가능. 제출 중 version이 바뀌면 최신 조회 후 재확인.
- 동일 사용자·version·항목 제출 멱등, 선택 거부(false)도 명시적 값으로 저장. 동의 철회는 별도 계약이며 재동의와 구분.
- 임시 계정은 명시적 상태·TTL·정리 대상으로 관리할지 BE와 합의. 현행 OAuth 계정 생성 시점과 refresh/푸시 등록·알림 실행 경계를 함께 검토. 미합의 수명 숫자를 먼저 넣지 않음.

오류 처리 후보(최종 status/code는 OpenAPI에서 확정):

| 의미 | FE 처리 |
|---|---|
| 미확인·연령 조건 미충족 | 정책/연령 안내에 머무름. 허위로 체크하도록 유도하지 않음 |
| 정책 version 변경 | 최신 문서/항목 조회 후 선택 재확인. 이전 true 재사용 금지 |
| 문자열 boolean·알 수 없는 항목 | 제출 오류 표시, 동의 완료 분기 금지 |
| 세션 만료 | 재로그인 후 상태 다시 조회. 임시 입력을 서버 확인 이력으로 전환하지 않음 |
| 구버전 클라이언트 | 지원 정책에 맞는 업데이트 안내/경로. 무한 재시도 금지 |
| 5xx·네트워크 실패 | 입력은 화면에서 보존 가능하되 서버 상태를 재조회하여 중복 제출/응답 유실 처리 |

## Google/Naver 탈퇴 경계 회신

현재 실제 호출 순서는 `Google disconnect(google_id 존재 시) → Naver disconnect(토큰 존재 시) → 서버 DELETE`다. SDK 호출은 try 블록 앞에 있어 실패하면 서버 접수 전 종료한다. Naver 토큰 부재는 provider 연결 해제 증거가 아니다.

후속 설계 제안:

1. SDK 해제 결과와 서버 접수 결과를 별도 상태로 다룬다. Google/Naver SDK 오류를 자동 성공으로 바꾸지 않는다.
2. 같은 인증 세션에서 SDK 해제 성공 뒤 서버 통신 실패 시 반복 SDK 호출만으로 내부 삭제가 막히지 않게 재시도 상태를 검토한다. 이 상태를 계정/세션/탈퇴 의도에 묶고 계정 전환 시 제거한다. 단말 재시작 후 복구 방식은 별도 합의.
3. 서버 202·진행 중·응답 유실·401을 각각 구분한다. 현행 401 로그아웃은 실제 삭제 접수 증거가 아니므로 성공 문구로 표시하지 않는다. 상태 조회용 인증과 UI를 합의한 뒤 연결한다.
4. SDK 세션 없음/만료는 재인증·재시도·지원 경로를 제공하는 방향. SDK 실패 무시·server-first 등 순서 변경은 이번 제안만으로 적용하지 않는다.
5. 앱 접근 불가 지원 접수는 현재 CLI 기능이 아니므로 운영자 본인확인·권한/감사·신규 접수 경로를 별도 확정한다. 이메일 받기만으로 내부 삭제가 자동 시작된다고 안내하지 않는다.

프로그램 수정 전 실제 기기 SDK 시나리오 결과와 BE의 상태 조회 계약이 필요하다. 이번에 상태 저장 로직이나 provider 호출 순서를 변경하지 않았다.

## 검증·호환 배포

계약 확정 후 실제 fixture 기반 FE parser·application 라우팅 테스트부터 추가한다. 서버가 아직 구현하지 않은 DTO에 맞춘 생산 코드/가짜 완료 UI를 먼저 배포하지 않는다.

- 누락/false/null/문자열 true/잘못된 version/중복·동시 제출/응답 유실/5xx.
- 기존 사용자/재가입 UUID/가입 프로필 재개/앱 재실행/계정 전환/구버전.
- 필수 미확인과 선택 거부, 공유 차단·철회의 다른 결과, version 교체.
- 제한 상태에서 문서·지원·탈퇴 접근. 나머지 API의 BE 강제 제한과 FE 분기 일치.
- SDK 무세션/만료/이미 해제/오류/해제 성공 후 서버 실패/202 응답 유실을 실기기 확인.

합의 → ADR/OpenAPI·고정 fixture → migration → 호환 BE → FE → 강제 적용. rollback 시 동의 이력을 없애거나 누락을 true로 바꾸지 않으며 강제 적용 정책을 별도 관리한다.
